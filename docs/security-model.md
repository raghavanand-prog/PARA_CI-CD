# Security Model

This document describes what "secure" means for this project in concrete,
verifiable terms: the controls in place, why each one exists, and where in
the repository it is implemented.

## 1. Defense in depth, by layer

| Layer | Controls | Where |
|---|---|---|
| Source code | Input validation, output encoding via JSON, no `eval`/dynamic require, parameterized nothing-to-inject (no SQL in this demo) | `app/src` |
| Authentication | bcrypt password hashing (cost 12), JWT with issuer claim and expiry, constant-time-shaped login response to resist user enumeration | `app/src/controllers/authController.js` |
| Transport | Helmet secure headers (CSP, HSTS, X-Frame-Options, etc.), rate limiting | `app/src/app.js` |
| Secrets | Never hardcoded; generated by Terraform (`random_password`), stored in Secrets Manager, resolved by ECS at container startup | `terraform/modules/security`, `terraform/modules/ecs` |
| Container | Multi-stage build, non-root user, minimal Alpine base, `readonlyRootFilesystem`, health check, no unnecessary packages | `app/Dockerfile`, `terraform/modules/ecs/main.tf` |
| Registry | Immutable tags, scan-on-push, KMS encryption at rest, account-scoped repository policy | `terraform/modules/ecr` |
| Network | Private subnets for compute, security groups scoped to the minimum required source/port, NAT for controlled egress only | `terraform/modules/networking` |
| IAM | One role per actor, every statement justified in a comment, no wildcard `Resource: "*"` except where AWS mandates it (documented inline) | `terraform/modules/iam` |
| Pipeline | Automated security gate enforced in code (not a manual click), fail-closed on any scanner or policy failure | `security/scripts/security-gate.sh`, `ci/buildspec.yml` |
| Observability | Structured, redacted logs; CloudWatch alarms on task health, error rate, latency | `app/src/utils/logger.js`, `terraform/modules/cloudwatch` |

## 2. The security gate, precisely

The gate is not a linter that prints warnings — it is a policy engine with
one job: decide, from evidence, whether this build is allowed to reach
production.

**Evidence** = one normalized JSON report per scanner
(`security/reports/<category>/*.json`), each with the shape:

```json
{
  "scanner": "trivy",
  "status": "completed | tool_missing | error",
  "generated_at": "2026-01-01T00:00:00Z",
  "findings": { "critical": 0, "high": 0, "medium": 0, "low": 0 },
  "details": [ /* up to 50 individual findings */ ]
}
```

**Policy** = `security/policy/security-policy.yaml`: a severity threshold
per category, editable without touching any script.

**Decision** = `security/scripts/security-gate.sh`:
1. Parse the policy. If it is missing, unparsable, or missing a required
   section, **abort hard (exit 3)** — the gate itself is broken, so nothing
   should be allowed to proceed on the assumption it passed.
2. For each enabled category, load its report.
   - Missing file, invalid JSON, or `status != "completed"` -> **fail
     closed** (counts as a violation), unless the policy explicitly opts
     that category into fail-open behavior.
   - Otherwise, compare `findings.<severity>` against
     `<category>.block_on_severity.<severity>` from the policy.
3. Secrets get their own zero-tolerance rule
   (`secrets.block_on_any_finding`) rather than a severity threshold,
   because a single leaked credential is unconditionally unacceptable
   regardless of how the scanner classified its severity.
4. Print a `SECURITY GATE RESULT` table and write a machine-readable
   summary, then exit `0` (all categories passed) or `1` (at least one
   failed).

**Enforcement** happens because `ci/buildspec.yml` calls
`security-gate.sh` as an ordinary shell command in the `build` phase. A
non-zero exit code fails that CodeBuild phase, which fails the CodeBuild
project, which fails the CodePipeline Build stage, which means the Deploy
stage — the one action that touches the running ECS service — never
executes. No human approval step exists to route around this; the only way
past the gate is to fix the underlying finding (or, as a documented and
audited last resort, adjust the policy thresholds themselves).

## 3. Fail-closed, not fail-open

A system that silently treats "I don't know" as "yes, deploy it" is not
actually enforcing anything — a network blip, an unpinned scanner version
that starts crashing, or a typo in a path is all it takes to bypass a
fail-open gate. This gate is fail-closed by default
(`gate.fail_closed_on_missing_report` and
`gate.fail_closed_on_scanner_crash`, both `true`):

- A scanner script that cannot find its tool writes a report with
  `status: "tool_missing"` and exits `1` — it does NOT silently skip itself.
- A scanner that errors mid-run writes `status: "error"` and exits `2`.
- The gate treats both of those, and a flat-out missing/corrupt report
  file, as a violation, identically to an actual policy threshold breach.
- This is validated directly by `tests/security/run-tests.sh`, which
  includes fixture scenarios for exactly these cases (see
  [`deployment.md`](./deployment.md) for how to run the vulnerability
  demonstration that exercises them against the real gate).

## 4. What is, and is not, covered

**Covered by automated scanning:**
- Static code patterns (Semgrep: injection, unsafe crypto, insecure
  deserialization patterns, etc.)
- Known-vulnerable dependencies (npm audit / OWASP Dependency-Check)
- Committed secrets, including in git history (Gitleaks)
- Misconfigured infrastructure as code (Checkov: public S3 buckets, open
  security groups, missing encryption, overly broad IAM, etc.)
- Known-vulnerable OS packages and language dependencies baked into the
  container image (Trivy)

**Not covered by this project (explicitly out of scope for the demo, noted
here so it isn't mistaken for an oversight):**
- Dynamic/runtime application security testing (DAST) against the live
  endpoint
- Fuzzing
- Formal penetration testing
- WAF / bot mitigation in front of the ALB
- Multi-account/organization-level guardrails (AWS Control Tower, SCPs)
- Automatic secret rotation (the JWT secret's rotation Lambda is not
  implemented; see `docs/troubleshooting.md` for how to add one)

See [`threat-model.md`](./threat-model.md) for the STRIDE-based analysis
this control set is derived from.
